# Android 保护方案源码核查

输出应能回答：谁在执行限制、靠什么权限、在哪种设备状态下生效、控制应用死后由谁解除、能否在当前项目复现。研究任务只授权读取与分析；安装 APK、授予管理权限或改手机配置沿用用户当前授权范围。

## 从失败模型找到代码路径

先区分普通进程回收、任务移除、包级 stopped、撤销无障碍与系统 crashed 状态。浏览当前 Android 官方机制；为每个候选固定提交，阅读 Manifest、服务生命周期、重启/守护、权限获取、限制执行和释放代码。沿调用链核实实现是否可达：注释掉的 suspend、未调用的辅助函数、TODO 或 README 承诺不能当成已部署功能。

来源记录用完整文件与行号永久链接。仓库/项目是否长期维护及有无目标系统验证独立判断；小型单设备案例可以做线索，不充当成熟方案的证据。需要挑选参考项目时读取 [已核查项目与入口](references/source-cases.md)，随后按任务重核当前代码。

## 按执行权限评估

| 路径 | 需要核实 |
| --- | --- |
| 普通应用 / FGS / 同包多进程 | 是否只是恢复普通回收，是否还依赖包未 stopped；不能凭进程分离认定包级隔离 |
| 厂商自启动/省电 | 可见设置、设备/ROM、相同动作对照，是否避免进入强停分支而非强停后自恢复 |
| ADB development 授权 | 实际授予条件、是否仅开发环境可用；manifest 声明不是授权成功 |
| Shizuku / root | 额外执行身份、授权与重启后的可用性；服务停止时限制怎样解除 |
| legacy Device Admin | 与 Device Owner/Profile Owner 分开；系统设置按钮灰掉不证明厂商划除遵守 |
| Device Owner / Profile Owner / 特权权限 | 部署条件、作用用户/配置文件与解除路径；不能为可行性测试清空个人手机或移除账号 |

重点查两类副作用：修复无障碍是否保留其他服务及写入失败是否回滚；系统 suspend/设备策略是否在控制进程死亡后继续生效，并可能超过专注期限仍无法放行。

## 形成适用性结论

对每个候选留下“固定提交/调用链、实际权限、适用状态、恢复与释放责任、许可证、本项目判断”。明确区分源码事实、作者注释、自己的推断与本机实验。没有找到可用证据就保留未知和范围，不把未找到写成绝对不可能。

选择足够解决当前问题、且满足当前设备条件的路径后再修改代码。只有配置足够时无需堆叠新的保活架构；引入 GPL 等源码前核查版权和分发义务。最终判定仍来自同一最终安装包的目标场景，不来自别人的成功案例。

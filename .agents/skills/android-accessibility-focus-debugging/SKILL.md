# Android 专注保护调试

目标是定位保护停止的实际层级，并验证当前设备上的恢复条件。开始先确认代码、安装包和手机当前状态；沿用已有修复与用户数据。正在进行的用户专注应保留，测试会话单独识别。手机操作按用户当前授权执行，新增权限通过可见系统界面确认。

## 区分失败层

分别记录 Home、切换应用、单卡上划、清空所有任务、设置强停、锁屏、重启中的哪一个操作。每次动作前后对照：

| 层级 | 需要的证据 |
| --- | --- |
| 包与进程 | stopped 状态、最新退出原因和时间；再次实验应产生新的退出记录 |
| 无障碍 | 设置中是否启用、系统是否实际绑定、是否 crashed；格式无法归属时记 unknown |
| 保护服务 | 前台服务是否存在、应用自己的状态接口是否可用 |
| 业务结果 | 当次会话/期限是否保留、未重开保护应用时能否实际拦截 |
| 覆盖层 | 提醒是否真实获得焦点并持续遮挡、知道了是否核实回到桌面 |

设置开关、进程存在、通知出现与实际拦截分别取证。只读摘要可用 [collect_protection_state.py](scripts/collect_protection_state.py)；用法和字段边界见 [诊断采集](references/read-only-diagnostics.md)。该脚本不操作手机界面、不改权限，也不能独立认证服务已绑定或核心验收通过。

## 按证据选择修法

- 普通回收：核查系统重新绑定、现有前台服务与厂商后台策略，再验证实际提醒。
- 包级强停/撤权：先检查条件是否遗漏，尤其厂商自启动与省电策略是不同设置。基于同一 APK、同一用户动作做对照；若要反向实验，先确认不会中断用户的真实专注。
- 当前手机条件能避免进入强停路径，不等于应用能抵抗真正强停。`START_STICKY`、独立进程、定时任务、开机广播的存在均不足以证明抗强停。
- 涉及小米时读取 [2026-10-15 条件性案例](references/xiaomi-autostart-case.md)。它用于选择检查项，不作为其他机型或当前手机的实时结论。MIUI 私有 app-op 编号仅可作经过核实的设备诊断线索。
- 需要引入外部项目实现时，核查源码、权限和设备条件；可配合 `android-protection-source-audit`，先判断适用性再改运行代码。

## 拦截与必要应用

通过实际应用窗口及根窗口包名判断前台，事件来源包名只作触发线索；避开输入法、系统窗口、通知及自己的覆盖层。横屏焦点暂未稳定时保留可见窗口证据，未知窗口不能直接撤掉已有提醒。

HOME 请求被接受后，确认允许窗口/桌面真正进入前台再撤提醒。验证快速重开同一受限应用仍可拦截。测试权限/省电页面的实际跳转目标：意图解析可能只返回中转 Settings，厂商再转到其他包。新增必要包应有本机证据并核对平台签名等可信身份，不只依据包名或 FLAG_SYSTEM。

## 排除测试干扰后验收

手机操作串行执行；上一段自动化确认结束后再导航。断连先排除 UIAutomator 对无障碍的暂停影响。模拟返回主界面时核对实际前台；`START_TASK_TO_FRONT` 可能返回旧任务栈中的设置子页面，必要时用已确认的主 Activity 配合 CLEAR_TOP 返回根页面。

开展长时锁屏或中断后恢复手机测试时，读取 [锁屏、到期与恢复操作](references/lock-and-resume-checks.md)：分别核对设备锁定、物理屏幕和保护期限；每段 UI 操作前重新确认前台，采样结束再读一次最终状态。

最终安装的同一 APK 要验证：核心失败动作后直接打开受限应用、提醒持续遮挡、确认回桌面、重复打开、横竖屏、必要应用、到期/退出放行。设备条件、本轮实测、旧证据和未通过项分开记录。界面在后台不等于 UI 进程已死；ADB 操作耗时不等于纯拦截延迟。核心项未过时保留候选状态。

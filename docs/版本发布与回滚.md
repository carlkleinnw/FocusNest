# 版本发布与回滚

用户要求每次完成更新都打标签。标签是代码快照；发布附件保存对应的安装包与网页演示，方便找到当时实际可用的交付物。

## 版本规则

- 功能/修复：先更新pubspec.yaml，例如0.2.4+6，再打v0.2.4-demo。
- 仅文档或发布说明修订：应用版本可以保持0.2.3+5，标签使用v0.2.3-demo.1、v0.2.3-demo.2等，逐次递增。
- 每次完成一轮更新都要提交并新增附注标签，不能只推代码而不推标签。
- 已发布标签不得移动、覆盖或删除；当前v0.2.3-demo保留为最初真机验证基线。
- CHANGELOG.md说明更新范围和验证结果。不要把历史验证、构建通过与本次新做的测试混为一谈。

## 新克隆安装一次推送检查

在项目根目录执行：

```powershell
./scripts/Install-ReleasePolicy.ps1
```

它仅修改本仓库的Git配置：安装.githooks/pre-push检查，并启用push.followTags。没有附注版本标签的分支更新会被本机拒绝；普通推送会带上可达的附注标签。新克隆需要重新安装，Git不会传播其他电脑的本地配置。

## 发布一轮更新

先按修改范围完成验证，再提交相关文件。不要把调试数据、密钥、缓存或APK提交到Git。

```powershell
git add <本轮修改的文件>
git commit -m "说明修改目的"
./scripts/Publish-Version.ps1 -Tag v0.2.3-demo.2 -Message "本轮文档修订及验证结果"
```

上面的标签仅为下一次同版本文档修订示例；功能变更应先更新应用版本。脚本检查干净工作树和版本一致性，创建附注标签，再原子推送当前分支与标签；服务端不支持原子推送或权限不足时会失败，不改用强制覆盖。

推送失败时，本地标签会保留。处理网络/权限问题后，可在同一提交重试同一命令；不能用force移动已有标签。GitHub默认分支为main，开发支线的发布需说明main是否已经包含该修改。

确认远程分支提交、标签指向和可见性之后，再报告上传完成。需要APK/网页包时，将匹配版本的构建及校验值放入GitHub Release附件。

## 查看历史版本

```powershell
git fetch origin --tags
git tag --list
git show v0.2.3-demo --stat
git switch -c inspect-0.2.3 v0.2.3-demo
```

最后一条命令创建新分支查看旧版本，保留main。切换前先提交当前工作；不要用reset --hard丢弃未保存修改。

也可以另建目录查看历史：

```powershell
git worktree add E:/FocusNest-history/0.2.3 v0.2.3-demo
```

目标路径应是新目录。回到正常开发使用git switch main。

若要撤销main上的具体修改，先分析提交依赖，用新的修复/撤销提交保留历史，再验证并打新的标签；不要强推旧提交覆盖远程main。

## 代码与手机数据分开

标签不会恢复手机SQLite数据库、宠物/计划记录或系统权限。原有APK可从对应Release取得；Android一般不会直接覆盖安装更低versionCode的APK。不要为回退代码直接卸载应用或清空用户数据，需要保留数据的应用降级应单独评估版本与数据库兼容。

本机 0.2.7 构建沿用 `ANDROID_USER_HOME=E:/DeveloperCache/focus_pet/android` 下已有的开发签名。覆盖安装前比较已安装 APK 与新 APK 的证书 SHA-256；不匹配就停止安装，先找回原签名，不通过卸载绕过。该路径和私钥不进入源码或发布包。回滚代码同样不会关闭/恢复小米自启动、省电或无障碍设置。

历史标签保存当时真实进度，其中旧原生版本存在已知漏拦截问题；需要实际体验时优先使用最新经验证的版本。

参考：[Git原子推送与附注标签](https://git-scm.com/docs/git-push)、[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。
